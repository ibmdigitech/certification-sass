## 1. Executive Summary

The codebase already implements a **transaction-safe Job entity with job-scoped certificate numbering** (`TSC-XXXX-XX` and `TSC-XXXX-##`). The `Job` model is genuinely the parent of `Certificate`, `Inspection`, `TrainingSession`, `Payment`, `Invoice` (via Payment), `DeliveryLog` (via Certificate), `ChecklistResult`, `InspectionReport`, `FailureWorkflow`, `Reschedule`, and `Timesheet`.

**What exists and is good (reuse, do not break):**
- `Job.jobNumber` is `@unique` + generated by `JobNumberService` inside a `$transaction` (`src/lib/services/job-number.service.ts:9-38`). Format `TSC-NNNNNNN`. Concurrency-safe.
- `Certificate.number` = `{job.jobNumber}-{sequence}` with `@@unique([jobId, sequence])` and a uniqueness check inside the same transaction (`src/lib/services/certificate-number.service.ts:6-56`). Sequence derived from `MAX(sequence)` inside the transaction — safe under concurrent requests. Never reuses revoked numbers implicitly (revoked certs keep their number; new ones get a new sequence).
- `validateLocationAccreditation` centralizes the Dubai→EIAC / Abu Dhabi→ENAS mapping (`src/lib/validation/location-accreditation.ts:13-37`). Already used by training courses/sessions. **Not yet used by jobs.**
- `JobService.getJobById` already eagerly loads `customer, engineer, certificates, inspections, trainingSessions, timesheets`.
- Inspection reports, failure workflows, and `InspectionReportSignature` all reference `jobId`.
- Multi-tenant pattern: every model has `companyId` and all queries filter by it.

**What is missing to meet the spec:**
- No `JobService` entity (job cannot carry multiple Training/Inspection service lines). `Job.type` is a free-text string, not a controlled service set.
- No real job detail UI (`/jobs/[id]` does not exist; `jobs/page.tsx:139-141` is an unimplemented stub).
- No job creation workflow with Service selection (Training / Inspection / Both) — `JobForm.tsx` takes a free-text `type` and an engineer only.
- `TrainingSession` has an optional `jobId` in the schema but **the create API cannot accept/set `jobId`** (`CreateSessionInput` lacks it; route handler spreads `...body` but the service ignores it). The standalone `/api/training/sessions` is auth-scoped (`getServerSession`) but not job-linked.
- `Inspection` is the actual inspection record (no separate "InceptionActivity"); it already has `jobId` FK. Certificates already support both `TRAINING` and `INSPECTION` types via `certificateType`.
- `Job` lacks `inspectorId` wiring through the API (schema has it, service does not expose it) and lacks `locationId` validation against accreditation at job creation.
- RBAC is not enforced client-side; `SessionProvider` is not mounted in the root layout. `companyId` is hardcoded to `1` in `jobs/page.tsx:14`, `inspections/page.tsx:95`, and the `jobs` API trusts a raw query param.
- Dashboard is fully mock data (`dashboard/page.tsx:1-134`).
- No job progress derivation, no closure policy, no audit trail writes for status transitions.
- `Timesheet.jobId` is optional (`Int?`); not enforced to the new model.

**Conclusion:** Reuse `Job` as the parent, extend with a lightweight `JobService` child to model multiple service lines, and wire `TrainingSession`/`Inspection`/`Certificate/Timesheet/Payment/Delivery` to it. No database reset, no duplicate modules.

## 5. RBAC, Multi-Tenancy & Security

- **Auth layer:** NextAuth v4, `CredentialsProvider`. `src/lib/auth/index.ts:1-76` (active) and a duplicate `src/lib/auth.ts:1-69`. Session payload: `{ id, role, companyId }` (`src/types/next-auth.d.ts:5-16` for Session, `:19-24` for JWT).
- **`/api/auth/[...nextauth]`** (`src/app/api/auth/[...nextauth]/route.ts:1-6`) wires `authOptions` from `@/lib/auth`.
- **Server-side auth usage is inconsistent:**
  - `src/app/api/training/sessions/route.ts:12` — uses `getServerSession`. ✅
  - `src/app/api/trainees/route.ts` — uses `getServerSession`. ✅
  - `src/app/api/jobs/route.ts` and `src/app/api/jobs/[id]/route.ts` — **do NOT call getServerSession**; `companyId` taken from raw query param (`searchParams.get('companyId') || '1'`). ⚠️ Trusts client for tenant — violates spec §11.
  - `src/app/api/certificates/route.ts` and `/api/inspections/**` — audited by task 1: certificates uses `companyId` in body; inspections reports use `companyId` in body.
- **Client side:** `Providers` (`src/components/providers.tsx:1-8`) exports a `SessionProvider` wrapper that is **never imported** into the root layout. `useSession` is therefore unavailable to client components. No role checks anywhere; `role` from session is written but never read on the client.
- **Tenant isolation** is correct in the DB layer (every query filters `companyId`) but the API entry points sometimes trust client-supplied `companyId` without server-side session validation.
- **Cross-tenant prevention:** schema enforces via `companyId` FKs + `@@unique([code,companyId])` etc. No model-level guard against attaching a training session / certificate to a job in another company except through the FK itself (which would fail). The `SyncQueue` and `CertificateNumberService` do check `job.companyId === companyId` (:21-23) — a good precedent to copy.

**Security findings (spec §11, §12):**
1. `jobs` API trust `companyId` from client params. Must add `getServerSession` + `session.user.companyId` and reject client-supplied tenant IDs.
2. `inspectorId` exists on Job schema but is never set via API (`CreateJobInput` in `job.service.ts:6-13` omits it).
3. `Job.type` is free text — no controlled service enumeration.
4. `SignaturePad.role` is display-only — no server role verification on signatures.
5. `inspectionReport.approve` endpoint sets `approvedBy` from body without authorizing the user's role.

## 8. Backward-Compatible Migration Proposal

Guiding principles (spec §2 + §11): **preserve existing records, backfill where the association is unambiguous, report unrecoverable records, never break standalone flows.**

### 8.1 Step-by-step (smallest safe changes)

**Step A — Add `JobService` model (service lines).**

```prisma
model JobService {
  id          Int      @id @default(autoincrement())
  companyId   Int
  company     Company  @relation(fields: [companyId], references: [id])
  jobId       Int
  job         Job      @relation(fields: [jobId], references: [id])
  serviceType ServiceType
  serviceCode String?
  description String?
  status      String   @default("PLANNED") // PLANNED, IN_PROGRESS, COMPLETED, CANCELLED
  requestedDate   DateTime?
  scheduledStart  DateTime?
  scheduledEnd    DateTime?
  assignedResponsibleId Int?
  completionDate DateTime?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  trainingActivity   TrainingActivity? @relation(fields: [trainingActivityId], references: [id])
  trainingActivityId Int?
  inspection         Inspection?       @relation(fields: [inspectionId], references: [id])
  inspectionId       Int?

  @@unique([jobId, serviceType]) // one service line per type per job
  @@index([companyId, jobId])
  @@index([companyId, status])
}

enum ServiceType {
  TRAINING
  INSPECTION
}
```

Rationale: keeps a single parent per ordered job; allows 1 or 2 service lines. `serviceType JobService @@unique([jobId, serviceType])` enforces the "Training only / Inspection only / Both" cardinality. The spec *suggests* `TrainingActivity`/`InspectionActivity` as conceptual children; `Inspection` already plays that role for inspections, so we point `JobService.inspectionId` → `Inspection` and add a thin `TrainingActivity` only where a course/session grouping beyond the existing `TrainingSession` is needed.

**Step B — Extend `TrainingSession.jobId` to required + set via API.**

Schema already has `jobId Int?`. Backfill: for sessions whose `jobId` is null but `trainingId`→`Training.jobId` is non-null, copy it. Report remaining nulls for review. Then expose `jobId` in `CreateSessionInput`. Until tightened, leave nullable.

## 10. Risks to Existing Data

1. **Hardcoded `jobId: 1` in inspection page** (`inspections/page.tsx:164,281`). Existing report/failure records already reference `jobId=1`. A migration that makes `InspectionReport.jobId` required-but-unlinkable would orphan reports if job 1 is deleted. Mitigation: do not delete job 1; backfill is identity (they already point at it).
2. **`TrainingSession.jobId` optional + unused by API.** Sessions created standalone (not from a job) will have `jobId=null`. New UI will set it; legacy sessions remain orphaned from jobs but still queryable standalone. Accept and report.
3. **Certificate `jobId` is required today** (`:491`). Every existing certificate already links to a Job — good. Numbering is already job-scoped. No migration needed for numbering.
4. **`Inspection` has required `jobId`** (`:231`). Existing inspections already link to a Job. Good — no backfill gap.
5. **Company 1 is the seed.** All stub pages use `companyId=1`. Real multi-tenancy only works once session `companyId` is trusted server-side in jobs/inspections/certificate endpoints.
